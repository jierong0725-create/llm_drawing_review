# LLM 三维协同图纸审核系统 — 概念设计

## 背景与核心问题

传统工程图纸 LLM 审核的瓶颈不是 LLM 不够聪明，而是**输入信息不足**：

- 2D 图纸是高度符号化的语言，丢失了三维空间关系
- LLM 不知道零件的功能意图（哪个面是配合面、公差要求从何而来）
- 零件之间的装配关系、周边约束在单张图纸中无法体现

目标：让 LLM 在审图前，真正理解零件的三维结构、配合关系和设计意图。

---

## 核心思路：人机协同的三维审图会话

### 整体流程

```
上传 STEP 文件
      │
      ▼
阶段一：LLM 主动探索 3D 模型（自主理解）
      │
      ▼
阶段二：人机对话确认设计意图（协同补充）
      │
      ▼
阶段三：汇总理解上下文 → 驱动图纸审核（应用输出）
```

---

## 阶段一：LLM 主动探索 3D 模型

### 机制

LLM 通过 **Agentic Tool Use** 主动控制 3D 渲染器，像人类工程师拿着零件翻转查看一样，自主决定下一步看哪个视角。

```
LLM 内部探索过程（对用户可见）：

"先看整体形状..." → render_view(等轴测)
"这是回转体零件，看看内腔..." → render_section(YZ 剖面)
"发现台阶孔，确认深度..." → measure_feature(孔深)
"有 4 个均布小孔，应该是安装孔..." → render_view(俯视图)
"初步判断：法兰类零件，核心功能面是内孔和端面"
```

### LLM 工具集

| 工具 | 说明 | 关键参数 |
|------|------|----------|
| `render_view` | 渲染指定视角截图 | azimuth, elevation, zoom, highlight_faces |
| `render_section` | 生成剖面图 | plane (XY/YZ/XZ), offset |
| `render_exploded` | 生成爆炸图 | explode_distance, focus_part |
| `measure_feature` | 测量几何特征 | feature_id, measure_type |

### 与预设截图方案的区别

- **预设方案**：固定渲染 10-15 张视角图一次性送入，LLM 被动接受
- **主动探索**：LLM 知道自己不知道什么，主动提问，按需获取视角
- 效果更好，尤其对复杂装配件

## 阶段二：人机对话确认设计意图

### 交互界面

```
┌─────────────────────────────────────────────────────┐
│                    前端页面                          │
│                                                     │
│  ┌──────────────────┐    ┌────────────────────────┐ │
│  │   3D 模型视窗     │    │      对话区域           │ │
│  │                  │    │                        │ │
│  │  [用户可自由旋转]  │◄──►│  LLM：我正在看内孔    │ │
│  │                  │    │  底部，这是盲孔吗？     │ │
│  │  ← LLM 控制视角  │    │                        │ │
│  │    同步显示给用户  │    │  用户：是的，用于安装   │ │
│  │                  │    │  轴承，需与外圆同轴     │ │
│  │  [高亮显示配合面] │    │                        │ │
│  │                  │    │  LLM：明白，我去确认   │ │
│  │                  │    │  图纸上的同轴度标注...  │ │
│  └──────────────────┘    └────────────────────────┘ │
│                                                     │
│  ┌─────────────────────────────────────────────────┐│
│  │  已提取的设计意图（实时累积）                      ││
│  │  ✓ 内孔：轴承安装面，与外圆同轴，公差 ≤ φ0.02   ││
│  │  ✓ 底面：装配基准，粗糙度 Ra 1.6               ││
│  │  ? 侧面安装孔：用途待确认                        ││
│  └─────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────┘
```

### 对话模式示例

```
LLM：我注意到内孔有两段不同直径（φ50 和 φ45），
     [视窗自动切到剖面图并高亮这两段]
     请问这两段的功能分别是什么？

用户：φ50 段是轴承外圈压入面（过盈配合），
     φ45 段是油封位（间隙配合）

LLM：明白了。φ50 段的表面粗糙度应该在 Ra 0.8 以下？

用户：对，要求 Ra 0.4

LLM：[记录] → 用于审核图纸上该面的粗糙度标注是否正确
```

LLM 不只在获取信息，同时在**实时验证自己的判断**，对话效率高。

### 关键设计：3D 视角同步

- LLM 调用 `render_view` 时，后端渲染截图供 LLM 分析
- 同时通过 **WebSocket** 将相同的视角参数推送到前端
- 前端 Three.js 同步旋转到该视角，用户看到 LLM "在看哪里"
- 用户也可自由旋转，不影响 LLM 的探索

## 阶段三：汇总设计意图 → 驱动图纸审核

### 输出结构（设计理解文档）

```json
{
  "part": "法兰轴承座",
  "functional_surfaces": [
    {
      "feature": "内孔 φ50H7 段",
      "function": "轴承外圈压入面",
      "mate_type": "过盈配合",
      "critical_dimensions": ["直径", "圆柱度", "表面粗糙度"],
      "expected_roughness": "Ra ≤ 0.4",
      "confirmed_by": "用户对话"
    },
    {
      "feature": "内孔 φ45 段",
      "function": "油封位",
      "mate_type": "间隙配合",
      "critical_dimensions": ["直径", "表面粗糙度"]
    }
  ],
  "assembly_datums": {
    "A": "底面（与箱体贴合）",
    "B": "内孔轴线（主定位）"
  },
  "open_questions": []
}
```

### 审核阶段的质量提升

有了这份文档之后，LLM 审图时具备：

- 每个尺寸的**功能意图**（知道为什么有这个公差）
- 关键配合面的**精度预期**（能判断公差是否合理）
- 装配基准的**物理含义**（能理解形位公差的约束逻辑）

审核结果从"符号层面的检查"升级为"设计意图层面的验证"。

## 技术架构

```
前端
├── Three.js + occt-import-js（STEP 直接在浏览器渲染，交互流畅）
├── WebSocket 客户端（接收 LLM 视角同步指令）
├── 对话 UI
├── 实时设计意图累积面板
└── 3D 标注层（高亮面、空间标记）

后端
├── pythonOCC（服务端渲染，为 LLM 生成截图）
├── Claude API — tool_use 多轮（探索 + 对话 + 审核三阶段）
├── WebSocket 服务（同步 LLM 视角到前端）
└── 会话状态管理（记录已确认的设计意图）

数据流
STEP 上传 ──→ 前端加载（Three.js，交互用）
           └─→ 后端加载（pythonOCC，LLM 渲染用）

LLM 调用 render_view
    ├──→ 后端渲染 → 截图返回给 LLM（分析用）
    └──→ WebSocket 推送视角参数 → 前端 Three.js 同步旋转
```

### 前后端分离渲染的理由

前端用 Three.js 实时交互渲染，后端用 pythonOCC 给 LLM 渲染截图，两者用**视角参数同步**而不是传递图片。这样：

- 前端始终是流畅的交互式 3D，体验好
- LLM 拿到的截图质量可控（可加高亮、标注、剖面等）
- 网络传输量小（只传参数，不传图片帧）

## MVP 最小可行版本建议

优先级排序：

1. **后端 pythonOCC 渲染服务** — LLM 探索的基础
2. **Claude tool_use 多轮对话** — 探索 + 对话逻辑
3. **前端 Three.js 3D 视窗** — 用户可见的 3D 交互
4. **WebSocket 视角同步** — 人机协同的关键体验
5. **设计意图结构化提取** — 连接对话与审核的桥梁
6. **对接现有图纸审核流程** — 闭环

---

## 核心价值总结

| 传统方式 | 本方案 |
|----------|--------|
| LLM 只看 2D 符号 | LLM 主动探索 3D 模型 |
| 设计意图靠人工填写 | 设计意图从对话中自动提取 |
| 审核是符号层面的检查 | 审核是设计意图层面的验证 |
| 用户与 LLM 信息不对称 | 用户与 LLM 共享同一个三维视角 |
| 静态单次分析 | 动态协同探索 |
